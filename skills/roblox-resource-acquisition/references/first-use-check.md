# First-use freshness check

Read before a needed Roblox library or development tool's first use in a task, including already adopted resources. This is a source check, not acquisition or full lifecycle reconciliation. The [maintenance policy](on-demand-maintenance.md#approved-authority) supplies applicable correction authority only when a repair is needed.

1. Resolve the needed resource's canonical identity and actual installed/project-pinned version, commit, or source state. Limit the check to resources the task will use; do not survey the whole tool list or dependency graph.
2. Read its canonical releases/package source and the documentation relevant to the intended use. Compare the latest stable release with the adopted target, separate preview channels, and verify that reusable instructions match the version actually used. If no stable release exists, record the current maintained source marker and date explicitly rather than inventing a version.
3. Record the identity, installed/pinned selector, latest stable release or dated maintained source, canonical URLs, UTC review time, and task-relevant guidance changes or compatibility concerns using [source observations](#source-observations) below. An adequate acquisition/source review already performed in this task satisfies the check. Reuse it within the task while its source, target, claim, and assumptions remain unchanged; changed inputs require a focused recheck. A previous task's observation is history, not this task's first-use check.
4. Report task-relevant new releases, fixes, features, breaking changes, or guidance drift. Keep unchanged checks quiet. Preserve project pins and valid exact-target execution proof; checking availability does not authorize installing, upgrading, replacing, or adopting a new release. Requalify or rerun proof only for evidence invalidated by an authorized change or demonstrated defect.
5. If a lookup fails, use the bounded evidence-route fallbacks in [search-playbook.md](search-playbook.md#when-an-evidence-route-fails), then disclose unavailable currentness precisely. Continue only where reliable evidence for the unchanged exact target supports the task. An unknown material identity/version, current block, incompatible instruction, or hard defect still stops dependent use; a failed freshness lookup alone does not erase valid execution proof.


## Source observations

Keep source observations outside skill discovery and runtime packages. Use an existing authoritative observation location when supplied; otherwise append to `<project-root>/.agents/roblox/resources/maintenance/source-observations.jsonl` for project claims or `~/.roblox-resources/maintenance/source-observations.jsonl` for shared parent/upstream claims. Each JSON line uses `format: roblox-skill-source-observation-v1` and records subject, claim, canonical source URL, reviewed source selector/marker, UTC observation time, stable/beta channel, outcome, and pointers to candidate/proof/proposal artifacts when applicable. Outcomes may be unchanged, correction-pending, decision-needed, lookup-unavailable, or applied. Existing entries are history; append the successor.

This observation log is not a second lifecycle registry. Keep resource identity, project choice, verification and host adoption in their authoritative schema-v3 record or supplied registry. Observe new release facts separately from the adopted target. Do not create a live resource record merely to log a parent-source review. An inaccessible observation destination is a recording blocker, not proof that the source was checked or the correction applied.
